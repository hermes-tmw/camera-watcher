# Camera Watcher

This is a Python/Flask API wrapper to manage a repository of video clips to support video machine learning experiments. In this case the video is taken from a security camera.

Clips are generated by the [Motion Project](https://github.com/Motion-Project/motion) motion binary.  

## Setup

Now, with Docker!! 

```
docker compose pull
docker compose build
docker compose up
```

### Operator configuration

`etc/watcher.cfg` is git-ignored (it carries the live DB password and API
keys). Copy the committed template and fill in real values:

```
cp etc/watcher.cfg.example etc/watcher.cfg
```

At build time the Dockerfiles bake `etc/watcher.cfg` when present and fall
back to `etc/watcher.cfg.example` otherwise, so a clean clone always builds.
At runtime every service bind-mounts `./etc` over `/usr/local/etc`, so the
file the containers actually read is your local `etc/watcher.cfg`.

### Machine verification

`make build` builds every service image (io first — Dockerfile-video derives
from its `camera-watcher-io` tag), `make test` runs the stealthcam test suite
(140 tests, stdlib unittest) against the committed example config. There is
deliberately no `make run`/`start` target: `docker compose up` boots real
workers against the production database.

`hermes verify` detects this Makefile and runs build → test (no start phase).
It passes on a clean clone with no local-only files. On hosts that also run
the live stack, use `hermes verify --skip-start` if a start phase is ever
added; today the recipe has none by design.

## Dashboard thumbnails

The `/browser` list serves lazily-generated thumbnails (downscaled to ~320px
JPEG) instead of the full-resolution frames, and nginx serves static images
with `Cache-Control: public, immutable` (GUID filenames are immutable).

Thumbnails are generated on first request and cached under
`LOCAL_DATA_DIR/thumb/`, keyed deterministically from the source path. They
are regenerable, so purging them is always safe (no data loss).

Optional `[thumb]` knobs in the app config (`watcher.cfg` / `application.cfg`):

| Key           | Meaning                                              | Default |
|---------------|------------------------------------------------------|---------|
| `MAX_COUNT`   | Max cached thumbnails (oldest deleted first)         | 20000   |
| `MAX_BYTES`   | Max total bytes of cached thumbnails (0 = unlimited) | 0       |
| `MAX_AGE_DAYS`| Delete thumbnails older than N days (0 = never)      | 0       |

The purge check runs lazily inside the thumbnail route, throttled to once per
minute. Unset/0 disables that limit.
